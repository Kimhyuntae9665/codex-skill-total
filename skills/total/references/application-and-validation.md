# 적용과 검증의 증거

## 변경 범위와 기록

작업 폴더에 원문 요청·고정 패킷·실제 역할 결과·통합·시도 기록을 보존한다. 프로젝트 결과물 규칙이 없으면 중간 자료는 `work/total/<run>/`, 전달물은 `outputs/`를 사용한다. 진단 기록을 대상 소스나 최종 제출 문안에 삽입하지 않는다. 단순 변경은 간단한 적용 지도와 diff로 충분하다.

채택한 개선의 변경 파일과 실제 관찰 결과를 연결한다. 예: 오류 메시지 연결 수정 → 잘못된 입력으로 오류를 발생시켜 입력 항목·메시지·포커스를 확인. 임의 KPI를 개선 성과로 쓰지 않는다. 검증 실패한 변경을 복구할 때 자신의 변경만 분리하며 사용자 변경을 되돌리지 않는다.

## 프로젝트

- Graphify 관계는 현재 소스에 근거해 확인한다. graph.json의 필드가 버전별로 다를 수 있으므로 실제 데이터를 읽는다. 지원되지 않은 입력·언어와 backend 부재를 숨기지 않는다. 조사 추출은 분석 파일을 생성하므로 순수 조회와 구분한다.
- Windows에서 POSIX 예시를 그대로 실행하지 않는다. Graphify는 절대 exe, UIUX는 search.py와 사용 가능한 Python, Impeccable은 절대 .cmd, Archify는 Node와 절대 bin/archify.mjs를 사용하고 cwd는 대상 프로젝트로 유지한다. 세부 명령은 각 스킬의 현재 진입점을 따른다.
- UIUX 검색 결과의 제품·모드·패턴을 대상과 맞춘다. 디자인 시스템 생성은 앱 개선 구현과 별개다.
- Impeccable context 실패 시 원본이 요구하는 실패 메시지를 먼저 알리고 기존 PRODUCT.md/DESIGN.md·실제 화면을 읽어 진행한다. 부분 개선과 전체 재설계를 구분한다.
- 핵심 동작을 실행한다. 적절한 기존 테스트·빌드를 수행하며 단순 서식 변경마다 구현과 같은 새 테스트를 만들지 않는다. 해당 기능의 오류·빈 상태·초기화·입력별 계산도 확인한다.
- Archify는 실제 이해에 도움이 될 때 추가한다. 관계를 소스/제품과 대조한 후 finalize를 실행하고 종료 코드·receipt·브라우저 증거·visualReview 상태를 구분한다. 자동 검사만으로 육안 검수를 완료했다고 쓰지 않는다.

Archify를 화면 수정 전에 쓰는 선택지는 한 흐름의 복사본으로 작게 검증한다. 원본을 보존하고 근거 있는 상태 전이를 정리해 누락된 안내·수정 위치를 특정한다. 수정 후 동일 조작에서 표시 상태·설명이 실제 동작과 일치하면 유지한다. 도식이 수정 위치나 확인 기준을 구체화하지 못하면 선행 배치를 철회한다. 이 선택지의 효용은 실행 관찰 전까지 검증 보류다.

## 포트폴리오·문서

사용자 형식·지침이 우선한다. 채용 자료는 사용자가 제공한 현행 채용/프로젝트 지침을 적용하고 기존 경험을 해당 회사를 위해 새로 만들었다고 바꾸지 않는다. 업무 연결은 공식 공고 또는 확인한 목표 업무에 근거하며 미확인 공고에 근거한 문장으로 표시하지 않는다.

신규/전체 재구성은 [포트폴리오 제작 지침](portfolio-guidance.md)에 따라 실제 업무 시뮬레이션을 검토한다. 기존 자료만/새 개발 없이 제약은 지키고 확장 제안은 분리한다. 합성 데이터·데모·실측·운영 성과를 구분한다.

최종 렌더링에서 요구된 페이지 수·사례별 직무 연결 문장·모든 스크린샷 바깥 네 변의 연속 테두리·캡션 분리·주요 시뮬레이션 화면/구조도의 관찰 안내와 실제 요소에 닿는 연결선을 전체 보기와 100% 보기로 확인한다. 원본 화면의 실제 내용을 임의로 고치지 않는다. 자소서·이력서 서술문까지 수정할 때 사용자가 지정한 윤문·사실 검증 지침을 적용한다.

UI 전용 스킬을 PDF 내부 편집기로 취급하지 않는다. 필요한 기존 문서/PDF 도구를 함께 사용하고 반영 결과를 최종 형식에서 확인한다. 대화형 HTML은 PDF와 별도 산출물이며 경로를 구분해 전달한다.

## 정직한 완료

Impeccable의 합동 첫 검사·한 번 수정·한 번 확인 상한을 우회하는 반복 루프를 만들지 않는다. 남은 결함은 보고한다. 요청된 핵심 개선이 blocked면 부분 완료, review-only면 원본 수정 없이 지도·제안까지만 반환한다. Council 완료와 실제 개선 검증 완료는 별개다.
